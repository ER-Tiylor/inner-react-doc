# 组件综合评估

## 介绍

本文档基于当前 `src/components` 目录下组件源码的实际实现情况进行评估，评分聚焦于组件封装质量，而不是业务价值本身。

评分维度如下：

1. 功能性
2. 设计与架构
3. 可维护性 & 代码质量

评分规则：

- 5 星为满分
- 综合分按 3 个维度的简单平均值计算
- 本页结论基于当前仓库实现，不代表组件未来演进后的最终状态

## 评分口径

### 功能性

重点看组件是否解决了明确问题、能力是否完整、是否覆盖真实业务场景。

### 设计与架构

重点看组件边界是否清晰、配置设计是否合理、是否具备复用性和扩展性。

### 可维护性 & 代码质量

重点看类型定义、内部复杂度、实现一致性、可读性、隐式约定数量、后续改造成本。

## 单项点评

### 第一梯队

| 组件         | 结论                                                                                                 |
| ------------ | ---------------------------------------------------------------------------------------------------- |
| `ProTable`   | 功能覆盖最完整，已经形成业务列表页基础设施，搜索、表格、树筛选、页配置、权限、汇总等能力整合度很高。 |
| `ProForm`    | 配置驱动思路清晰，普通表单与卡片表单都具备较好的复用潜力，查看模式和依赖联动也比较成熟。             |
| `PageTabs`   | 标签页管理和页面缓存联动做得比较到位，比较贴近真实中后台工作台场景。                                 |
| `FormUpload` | 上传、回显、模板下载、预览、私有/公共文件桶等能力完整，业务可用性很强。                              |
| `KeepAlive`  | 对 `react-activation` 做了较实用的业务封装，解决了多标签缓存和页面回收问题。                         |

### 第二梯队

| 组件           | 结论                                                                       |
| -------------- | -------------------------------------------------------------------------- |
| `EditTable`    | 可编辑表格能力较实用，但内部条件分支较多，类型和渲染逻辑还可以继续收敛。   |
| `SearchInput`  | 远程搜索选择封装实用，接口和表单适配比较贴近业务，但有一定隐式约定。       |
| `UploadDrawer` | 场景明确且可用，不过与 `FormUpload` 存在重复逻辑，后续适合抽公共上传核心。 |
| `Contract`     | 业务流程完整，但组件内部耦合了较多列表和弹窗逻辑，业务专用性偏强。         |
| `PDFViewer`    | 功能上够用，但动态加载外部脚本和内部状态管理方式还有优化空间。             |

| 组件             | 结论                                                                 |

| `ImportModal`    | 可用性尚可，但封装边界和类型精度一般。                               |
| `Address`        | 具备业务价值，但存在接口、store 和级联逻辑的直接耦合。               |

### 第四梯队

| 组件          | 结论                                                     |
| ------------- | -------------------------------------------------------- |
| `ConfimModal` | 功能单一且定制度低，适合作为局部复用件，但抽象层次较浅。 |
| `NavFooter`   | 只是静态页脚展示，维护成本低，但组件能力很弱。           |
| `SearchTable` | 当前实现更像未完成的模板骨架，文档和功能都应继续完善。   |

## 结论

从整体看，当前组件库的核心价值主要集中在两类组件：

- `ProTable`、`ProForm` 这类中后台页面基础设施组件
- `FormUpload`、`KeepAlive`、`PageTabs` 这类强业务通用能力组件

相对薄弱的部分主要有两类：

- 展示型薄组件过多，抽象价值有限
- 个别组件存在业务逻辑、状态管理、接口请求和 UI 强耦合的问题，后续如果要继续建设组件库，建议优先做公共能力下沉和类型收敛

## FAQ

为什么有些组件功能很简单，但可维护性分数不低？

因为可维护性看的不是功能多少，而是实现是否简单、稳定、容易理解和修改。像 `Auth`、`FooterButton`、`NavFooter` 这类组件虽然能力不强，但实现成本和维护风险都比较低。

为什么 `ProTable` 不是三个维度都满分？

它的功能性非常强，但内部也存在较多职责聚合、隐式约定和配置分支，因此在“设计与架构”“可维护性 & 代码质量”上仍有继续优化空间。
