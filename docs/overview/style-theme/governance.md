# 样式与主题治理建议

## 背景

BMS 当前已经把 `src/antd` 和 `ProForm`、`ProTable` 这类组件当成业务基础设施使用，但样式层的治理状态并不统一。

从现状看，至少同时存在以下几类手段：

- 全局主题入口：`src/config/theme.ts`
- 全局覆盖样式：`src/styles/theme.less`
- 局部 `ConfigProvider` 主题覆盖
- `antd-style` 的 `createStyles`
- `CSS Modules` 与 `:global`
- 少量原子化内联样式

问题不在于这些手段都不能用，而在于目前没有清晰分层，所以会出现：

- 同一个视觉问题可以被多种方式覆盖
- 局部组件容易绕过全局主题规则
- `viewMode`、空值展示、表格、Tab 等基础交互没有统一样式协议
- 后续想支持多公司定制时，缺少稳定的主题注入边界

## 目标

这项治理的目标不是立即重写全部样式，而是先建立清晰规则：

1. 让当前项目中的样式覆盖尽量统一
2. 为未来“同一套标品按不同公司主题定制”预留清晰边界
3. 避免未来抽 npm 包后再返工一次样式体系
4. 尽量顺应 Ant Design 5 的 token 方向，并对未来版本演进保留空间

## 当前问题归纳

### 1. 全局、局部、组件内覆盖边界不清

例如：

- `App.tsx` 里有全局 `ConfigProvider`
- `ProForm`、`PageTabs` 等组件内部又有局部 `ConfigProvider`
- `theme.less` 里又有全局类名覆盖

这会导致：

- 某些视觉风格只能在组件内部改
- 某些全局 token 改了以后，局部组件完全不响应
- 主题来源不唯一

### 2. token 与选择器覆盖混用，但没有优先级规范

当前既有：

- token 配置
- 组件级 token
- 直接写 `.febms-*` 类选择器
- `:global` 覆盖 antd 内部类名

没有规范时，常见结果是：

- 能用 token 的地方也被硬编码 CSS 覆盖
- 升级 antd 后内部类名变化，历史覆盖失效
- 组件样式逐渐变得难以定位来源

### 3. 组件层已经形成“样式协议”，但没有被显式抽象

例如 `src/antd` 里已经隐含了这些约定：

- `viewMode`
- 空值展示 `--`
- 一些统一 placeholder
- 表单只读展示形态

这些其实已经不是单纯样式，而是“视觉与交互协议”，应该被正式纳入治理。

## 可选治理策略

## 方案 A：继续混合使用，但补充约定

做法：

- 保留当前所有技术手段
- 补一份团队规范，限制使用场景

优点：

- 改造成本最低
- 不影响当前业务节奏

缺点：

- 历史包袱继续保留
- 规则容易被绕过
- 不利于未来多公司主题能力建设

判断：

- 只能作为短期过渡
- 不建议作为最终方向

## 方案 B：Token First + 语义层 + 局部受控覆盖

这是推荐方案。

核心思想：

1. 全局主题只负责设计 token
2. 基础控件层只消费语义 token，不直接散写品牌色
3. 组件局部允许覆盖，但必须受控并可解释
4. 全局选择器覆盖只保留少量兜底场景

这是当前最适合 BMS 的路线，因为：

- 能兼容现有 antd 5 体系
- 不要求你一次性把样式技术栈统一成一种
- 适合后续抽基础包与 Pro 包
- 也给未来多公司主题留出了入口

## 方案 C：全面转向单一 CSS-in-JS 方案

做法：

- 逐步把样式统一到 `antd-style` 或同类方案
- 减少 less/module.less 的存在

优点：

- 理论上主题切换和动态 token 能力更强
- 更接近 token 驱动体系

缺点：

- 成本高
- 现阶段会和现有大量 less/module.less 冲突
- 对当前团队习惯和代码存量不友好

判断：

- 可以作为长期演进方向
- 不适合作为当前第一阶段治理目标

## 推荐方案

推荐采用：**方案 B：Token First + 语义层 + 局部受控覆盖**。

## 推荐的样式分层

建议把样式治理拆成四层：

### 第一层：品牌与设计 Token 层

职责：

- 定义主色、成功色、警告色、字号、圆角、间距、背景、边框等全局设计变量
- 通过根级 `ConfigProvider theme` 统一注入
- 作为未来不同公司主题切换的主入口

建议放置位置：

- `src/config/theme.ts`
- 后续可演进为 `src/theme/presets/*.ts`

这一层只定义：

- 品牌 token
- 全局 token
- antd 组件 token 的统一映射

不应该承担：

- 单页面视觉修补
- 单组件特殊场景覆盖

### 第二层：语义 Token 层

职责：

- 把“设计 token”翻译成“业务组件可理解的语义变量”
- 例如：
  - 表单查看态文字色
  - 空值展示颜色
  - 表格头背景色
  - 页签激活态颜色
  - 页面容器背景色

这层很关键，因为未来不同公司换主题时，应该优先改语义映射，而不是逐个改组件。

建议形式：

- CSS 变量
- 或 TypeScript 常量对象
- 或两者结合

例如未来可以形成类似：

```ts
formViewTextColor
emptyValueColor
tableHeaderBg
pageTabsBg
layoutContentBg
```

注意：

- 这一层不是直接抄 antd token 名
- 而是定义“你们组件体系自己的语义名”

### 第三层：基础控件层

职责：

- `src/antd` 中真正有协议价值的基础控件只消费上面两层
- 不直接写死业务品牌色
- 不直接依赖页面局部覆盖来决定展示效果

这一层主要承载：

- `viewMode`
- 空值展示
- 默认 placeholder
- 统一尺寸与布局细节

也就是说，未来基础包抽出去时，应该把“样式协议”也一起带走。

### 第四层：业务组件与页面层

职责：

- 页面布局细节
- 业务弹窗差异样式
- 局部表格特殊高亮
- 和具体业务强相关的视觉处理

这层允许使用：

- `createStyles`
- `module.less`
- 少量局部 `ConfigProvider`

但前提是：

- 只能做局部差异
- 不能反向定义全局主题
- 不能把基础层 token 绕开后重新发明一套颜色和尺寸体系

## 推荐的覆盖优先级

为了减少混乱，建议明确样式来源优先级：

1. 根级主题 token
2. 语义 token
3. 基础控件默认样式
4. 业务组件局部样式
5. 页面级临时覆盖
6. 全局兜底覆盖

这里的原则是：

- 越靠上越稳定、越可复用
- 越靠下越应该谨慎使用

特别是全局兜底覆盖，应该被视为“最后手段”，而不是默认方案。

## 对不同技术手段的建议用法

### `ConfigProvider theme`

建议用途：

- 全局 token 注入
- 少量组件级 token 统一配置
- 主题切换的唯一上游入口

不建议：

- 每个复杂组件都自己包一层 `ConfigProvider` 改 token

规则建议：

- 根级 `ConfigProvider` 是主入口
- 组件内局部 `ConfigProvider` 仅用于确实属于组件协议的差异
- 局部 `ConfigProvider` 需要有明确白名单，不能泛滥

### `theme.less`

建议用途：

- 全局基础样式
- scrollbar、reset、prefix 级兜底类
- 非 token 可表达的少量兼容性修补

不建议：

- 承担主要主题能力
- 大量覆盖 antd 内部类名
- 写具体业务组件颜色和布局

### `module.less`

建议用途：

- 页面级或业务组件级局部布局样式
- 低复用、局部结构样式

不建议：

- 通过 `:global` 大量修改 antd 内部类名
- 承担主题层职责

### `antd-style createStyles`

建议用途：

- 与 token 强相关的组件局部样式
- 需要使用 `prefixCls`、动态主题、运行时计算的场景
- 高复用基础组件或 Pro 组件内部样式

判断标准：

- 如果样式明显依赖 token 和组件状态，优先 `createStyles`
- 如果只是页面布局块，优先 `module.less`

## 对未来“多公司定制”的前瞻设计

当前不必立刻做完整多租户主题系统，但建议现在就预留三层能力：

### 1. 品牌预设层

未来每家公司只需要提供一份主题预设，例如：

- 主色
- 辅助色
- 警告色
- 圆角风格
- 表格头背景风格
- 页面容器背景风格

即：

```ts
companyATheme
companyBTheme
companyCTheme
```

### 2. 语义映射层

不同公司不直接改每个组件，而是通过语义 token 映射：

- 公司 A 的 `tableHeaderBg`
- 公司 B 的 `tableHeaderBg`

这样改的是“语义层”，不是组件实现。

### 3. 组件可插拔覆盖层

对于少数公司特化场景，可以允许：

- 组件级样式覆盖包
- 或品牌级扩展样式文件

但原则是：

- 这层只能覆盖少量特殊需求
- 不能取代主主题系统

## 对 Ant Design 5 到未来版本的前瞻建议

这里不展开版本细节，只讲方向。

建议你们现在就坚持：

- 主题优先用 token 思维，而不是 less 变量思维
- 基础控件层优先消费 token / 语义 token，而不是硬编码颜色
- 避免强依赖 antd 内部 DOM 结构和内部类名
- 把 `viewMode`、空值展示、表格头、页签等协议显式化

这样无论后续是继续升级 antd 5 的小版本，还是未来面对更大样式策略变化，迁移成本都会更低。

## 第一阶段最小治理建议

如果只做一个务实的第一阶段，建议先完成这几件事：

1. 收拢主题入口
   保证根级 `ConfigProvider` 是唯一主主题入口。

2. 列出局部 `ConfigProvider` 白名单
   例如：`ProForm`、`PageTabs` 当前为什么要局部改 token，要不要保留。

3. 建立语义 token 清单
   先不要做很全，先覆盖：
   - 主色
   - 页面背景
   - 容器背景
   - 表格头背景
   - 页签背景
   - 查看态文字色
   - 空值文字色

4. 约束覆盖手段
   - 全局样式只做基础层和兜底
   - 组件 token 优先于 `:global` 覆盖
   - 页面局部样式优先 `module.less`
   - token 相关样式优先 `createStyles`

5. 先选两类组件做试点
   建议从：
   - `src/antd` 基础控件
   - `ProForm` / `PageTabs`
   开始

## 最终建议

当前最适合 BMS 的方向不是立刻统一成单一技术栈，而是先统一规则。

一句话总结：

- 用根级 token 管主题
- 用语义层管组件体系
- 用基础控件层承接统一交互协议
- 用局部样式处理业务差异
- 把全局覆盖降到最后手段

这条路线既能改善当前项目的样式混乱，也能给未来不同公司定制和 npm 包化预留出比较清晰的演进路径。
