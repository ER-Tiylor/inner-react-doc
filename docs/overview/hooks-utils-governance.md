# Hooks 与 Utils 治理建议

## 背景

BMS 当前已经沉淀出一批具备复用价值的 `hooks` 与 `utils`，但它们的状态并不完全一致：

- 有些已经具备较清晰的输入输出边界，适合直接写文档并推广复用
- 有些虽然使用频率高，但和 store、权限、请求链路耦合较深，更适合作为“治理对象”先收敛再推广
- 还有一些只是局部页面工具或历史遗留工具，不建议进入统一文档站

因此这部分内容当前更适合放在“治理规划”下，而不是直接升格成新的一级导航。

## 当前判断标准

一项 Hook 或工具是否值得进入文档站，建议至少满足以下条件中的大部分：

1. 在多个子应用或多个业务域出现过复用
2. 输入输出边界清晰，脱离具体页面也容易理解
3. 不依赖特定页面状态、临时接口返回结构或历史路由写法
4. 有稳定的使用姿势，而不是每个页面都要二次改造
5. 未来仍然会被继续使用，而不是过渡方案

## 第一批建议沉淀的能力

### 1. useQueryParams

路径：`src/hooks/useQueryParams.ts`

推荐理由：

- 职责单一，主要围绕 URL 查询参数读取与同步
- 使用成本低，容易被列表页、详情页、筛选页理解和接受
- 和业务 store、服务层没有强耦合

### 2. storage

路径：`src/utils/storage.ts`

推荐理由：

- `LStorage`、`SStorage` 边界明确
- 可直接作为多子应用共识工具
- 比零散调用原生 `localStorage` / `sessionStorage` 更利于规范化

### 3. dict

路径：`src/utils/dict.ts`

推荐理由：

- 字典转下拉选项、转搜索项是高频需求
- 非常适合作为组件层和业务层之间的数据整形工具
- 后续可以和 `useDataDict` 配套形成完整方案

### 4. useDataDict

路径：`src/hooks/vision/dataDict.ts`

推荐理由：

- 复用率高
- 和表单、表格筛选、状态展示关系密切
- 很适合作为业务通用 Hook 沉淀

当前问题：

- 与 store 耦合较深
- 对外依赖前提需要写清楚
- 更适合先文档化使用约定，再逐步抽象

### 5. permission

路径：`src/utils/permission.ts`

推荐理由：

- 路由、菜单、权限树处理是基础能力
- 这类逻辑通常散落在布局层与导航层，文档化价值高
- 适合整理成权限与菜单工具专题

### 6. useGoodsOwner

路径：`src/hooks/vision/goodsOwner.ts`

推荐理由：

- 在 BMS 体系内是高频业务通用能力
- 能减少页面重复处理货主相关数据
- 具备平台内部复用的现实价值

当前问题：

- 业务属性明显，不属于纯基础 Hook
- 与用户态、权限或 store 可能存在隐式约束

## 第二批：建议先收敛再推广

### utils.ts

路径：`src/utils/utils.ts`

这个文件中确实有一些值得复用的工具，例如：

- `generateUUID`
- `makeUuid`
- `createSpan`
- `enumToSelectOptions`
- `enumToObject`
- `stringToTime`
- `timeToString`
- `uniqBy`
- `deepClone`

但当前问题也很明显：

- 单文件承载过多职责
- 工具粒度不统一
- 有些函数偏底层，有些函数偏页面场景
- 类型与命名风格还不够整齐

建议：

- 先拆成更明确的分类，例如 `enum`、`time`、`collection`、`id`
- 再决定哪些进入正式文档

### projectUtils

路径：`src/utils/projectUtils.ts`

这里的手机号、邮箱、统一社会信用代码等校验能力具备复用价值，但目前更像表单校验工具集合。

建议：

- 先收敛成统一的校验工具模块
- 后续可作为表单校验规范专题的一部分输出

### findTreeChildId

路径：`src/utils/findTreeChildId.ts`

有实际用途，但偏场景化，适合在树形数据工具统一之后再决定是否独立文档化。

## 当前不建议进入文档站的内容

### useTreeData

路径：`src/hooks/useTreeData.ts`

问题：

- 抽象层级不够稳定
- 依赖具体数据来源和业务场景
- 目前更像局部页面能力，而不是可推广的通用 Hook

### request

路径：`src/utils/request.ts`

问题：

- 属于应用基础设施
- 和网络层、拦截器、登录态、错误处理深度耦合
- 不适合作为通用工具文档优先输出

### commonUrl

路径：`src/utils/commonUrl.ts`

问题：

- 本质是常量与接口地址组织，不属于可复用开发能力文档范围

### array / money 等零散工具

路径：

- `src/utils/array.ts`
- `src/utils/money.ts`

这类内容要么抽象还不够稳，要么体量偏小，暂时不值得单独在文档站占一个入口。

## 推荐的信息架构

当前阶段建议仍放在治理规划下，后续可以逐步拆成以下几类：

1. 通用 Hooks
2. 业务通用 Hooks
3. 基础工具
4. 表单与字典工具
5. 权限与路由工具

如果未来这部分内容增长到 8 到 12 篇以上，再考虑是否独立为新的一级导航，例如：

- 开发能力
- 通用能力
- 能力中心
