# 组件严格复评

## 介绍

本文档是在原有组件总结基础上的一版“更严苛标准复评”。

和上一版相比，这一版会明显提高评分门槛，重点关注：

1. 功能是否完整且边界清晰
2. 设计与架构是否具备长期平台化潜力
3. 可维护性 & 代码质量是否足以支撑多人长期协作

也就是说，这一版不是看“能不能用”，而是看“作为长期组件资产是否足够稳”。

## 更严苛的评分标准

### 功能性

不只看“功能多不多”，还看：

- 功能是否闭环
- 边界场景是否覆盖
- 对外协议是否稳定
- 是否真的适合复用，而不是仅在当前页面可用

### 设计与架构

更严格关注：

- 组件职责是否单一
- UI、数据、状态、业务逻辑是否过度耦合
- 配置设计是否一致、清晰、低心智负担
- 是否具备可演进性，而不是“先堆起来能跑”

### 可维护性 & 代码质量

更严格关注：

- `any` 和弱类型比例
- 隐式约定数量
- 命名一致性
- 重复逻辑
- 复杂逻辑拆分程度
- 后续测试和重构难度

## 严格版结论变化

和上一版相比，这一版有几个明显变化：

- `ProTable` 仍然是第一，但优势主要来自功能，不再是“全面领先”
- `ProForm` 依然靠前，但因为双结构配置和查看模式约定问题，被压了分
- `FormUpload`、`PageTabs`、`UploadDrawer` 这类“好用但耦合偏重”的组件分数下降明显
- `Auth`、`FormDigitRange`、`FooterButton` 这类小组件在架构和维护性上反而相对稳定
- `SearchTable` 因为当前实现过薄，在严格标准下几乎只能算未完成模板

## 分层复评

### A 档：高价值，但还没到“优秀平台组件”

| 组件        | 结论                                                                                           |
| ----------- | ---------------------------------------------------------------------------------------------- |
| `ProTable`  | 功能完整度最高，但内部聚合的职责过多，严格标准下更像“强业务基础件”，还不是非常干净的平台组件。 |
| `ProForm`   | 复用性不错，但普通表单和卡片表单是两套结构，查看模式协议也偏松散，长期看仍有统一空间。         |
| `KeepAlive` | 对多标签缓存场景很有价值，但本质上仍偏场景化封装，离通用基础设施还有一点距离。                 |

### B 档：业务很好用，但架构上还有明显欠账

| 组件          | 结论                                                                                     |
| ------------- | ---------------------------------------------------------------------------------------- |
| `FormUpload`  | 功能够强，但和 `UploadDrawer` 重复逻辑较多，上传、预览、地址转换等能力没有形成统一底座。 |
| `PageTabs`    | 实战价值高，但路由、缓存、标签管理强绑定，模块职责没有完全拆开。                         |
| `SearchInput` | 可复用性不错，但参数协议较隐式，长期扩展时容易出现“每个页面都要猜一下怎么传”的问题。     |
| `EditTable`   | 业务上可用，但单元格类型分支、编辑行为和状态逻辑都比较密集，阅读和改造成本偏高。         |

### C 档：可用，但更偏项目内业务组件

| 组件           | 结论                                                                   |
| -------------- | ---------------------------------------------------------------------- |
| `UploadDrawer` | 本身并不差，但在严格标准下重复实现和类型不一致问题会被放大。           |
| `Contract`     | 业务流程完整，但抽象层次不高，复用边界比较窄。                         |
| `FlowModal`    | 有明确场景，但本质是审批展示组件，不是高抽象度基础件。                 |
| `LogModal`     | 实用但直给，更多是业务弹窗能力，而不是可平台化的组件资产。             |
| `Address`      | 组件依赖 store、接口和级联逻辑，复用时上下文要求偏重。                 |
| `ImportModal`  | 功能闭环尚可，但 API 和实现的一致性、扩展性都比较一般。                |
| `SideMenu`     | 对布局有价值，但更像应用层组装组件。                                   |
| `NavHeader`    | 混合了主题、导航、用户态、退出登录、开发按钮等职责，严格标准下不够纯。 |
| `PDFViewer`    | 功能可用，但运行时动态加载外部脚本和内部渲染方式都不算很稳。           |

### D 档：小而简单，但抽象价值有限

| 组件             | 结论                                                                   |

## 严格版三维观察

## 1. 功能性复评

严格看功能性，真正能拿到高分的组件必须满足：

- 不只是“能用”
- 而是功能面完整、输入输出稳定、边界清晰、可复用

在这个标准下：

- `ProTable`
- `ProForm`
- `KeepAlive`
- `FormUpload`
- `PageTabs`

是功能面最强的一组。

但即便是这些组件，也并不是满分，因为：

- 有些功能耦合了项目上下文
- 有些能力依赖隐式约定
- 有些输出协议还不够稳定

## 2. 设计与架构复评

这一维拉分最明显。

很多组件在“能跑”层面没有问题，但在严格标准下会因为这些原因掉分：

- 组件职责不单一
- 页面逻辑直接塞进组件
- 请求、状态、UI 混在一起
- 配置结构前后一致性不足

这一维真正相对稳定的，反而是：

- `Auth`
- `FormDigitRange`
- `SearchTree`

因为它们虽然简单，但边界相对明确。

## 3. 可维护性 & 代码质量复评

这一维更强调长期协作成本。

主要扣分点包括：

- `any` 偏多
- 同类逻辑重复实现
- 命名不一致
- 类型声明和真实返回值不一致
- 某些高级能力缺少更清楚的中间抽象

因此：

- `ProTable`
- `FormUpload`
- `UploadDrawer`
- `Contract`
- `PDFViewer`

这类“功能强但内部复杂”的组件，在这条维度上普遍掉分。

## 最值得重新关注的 5 个组件

如果按严格复评结果，最值得优先做二次治理的是：

1. `ProTable`
   原因：最核心、收益最大，但也最需要架构收敛。

2. `ProForm`
   原因：最有机会形成稳定表单协议，值得继续平台化。

3. `FormUpload`
   原因：能力强，但应尽快抽公共上传核心。

4. `PageTabs`
   原因：高价值导航能力，但和缓存、路由耦合偏深。

5. `SearchInput`
   原因：这是高频基础交互组件，协议如果不收敛，后面会持续放大接入成本。

## 结论

严格标准下，这套组件体系的整体评价可以概括为：

- 已经形成了一批“强业务可用组件”
- 但真正达到“长期稳定平台组件”标准的还不多
- 最大的问题不是功能不够，而是抽象、边界、类型和一致性还没有完全收住

如果按更严苛的标准看，当前组件库更像：

- 一套已经很有积累的项目级组件体系

而不是：

- 一套已经成熟收敛的长期组件平台

这不是坏结论。相反，这说明后续最有价值的工作不是“继续铺数量”，而是“把已有高价值组件打磨稳”。

## FAQ

为什么严格版里有些简单组件反而名次不低？

因为严格标准会惩罚复杂但耦合重的实现。简单组件虽然能力弱，但如果边界清楚、逻辑直给、维护成本低，在“设计与架构”“可维护性”上反而不会太吃亏。

为什么 `ProTable` 第一名只有 `3.7/5`？

因为严格版不是在看“当前项目里是不是非常有用”，而是在看“放到长期、多人、跨页面、跨场景复用里，是否已经足够稳定和优雅”。`ProTable` 非常强，但离这个标准还有优化空间。
